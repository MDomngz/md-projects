Before you recruit

  • Confirm your study is covered under an existing PRA (Paperwork Reduction Act) generic clearance, or get it cleared, before recruiting. Don't run a survey or structured interview protocol with more than 9 members of the public without confirmed clearance.
  • Recruit through Perigean (or your team's approved panel) rather than ad hoc outreach, so consent and screening stay consistent across studies.

Collaboration Cycle checkpoints

  • Midpoint Review — validate the approach with platform stakeholders partway through.
  • Staging Review — a full accessibility, content, and design QA pass before launch.

  • Write screeners and discussion guides in plain language (VA content style guide, 6th-grade reading level) so recruiting itself doesn't create a comprehension barrier.
  • Note where a Veteran's journey extends beyond VA.gov into other government or community services — don't assume the task starts and ends inside your tool.

What is Deep Research?

Deep research is a Copilot agent that reads and analyzes actual research findings files across the va.gov-team repository to answer complex questions about what we learned from research — not just a smarter search, but a synthesis across every study it finds relevant.

Critical prerequisite: attach the repository. You must attach the va.gov-team repository to your Copilot chat before using deep research. Without this step, Copilot will make assumptions and pull information from the public web instead of analyzing the actual research files in the repository.

How to attach the repository

  • Click the bookmark icon (📖) in the Copilot chat input area.
  • Search for and select department-of-veterans-affairs/va.gov-team.
  • The repository will appear as a pill/tag in your chat input area.

You only need to do this once per chat session — confirm it's attached by looking for the va.gov-team pill/tag in your chat input.

Code search vs. deep research

Code search is fast but limited — it can list pain points it finds mentioned, but with no frequency counts, no participant quotes, no implementation tracking, and no cross-study synthesis. Deep research is comprehensive: for a query like "top pain points in disability claims research," it can return which of, say, 17 studies mentioned each pain point, direct participant quotes, whether it was later addressed (with the studies that addressed it), cross-cutting themes, and links to every source file analyzed — at the cost of taking a few minutes instead of a few seconds.

ToolResponse timeDepthBest for
Summary files< 5 secondsMetadata onlyQuick lookups
Code search5–15 secondsLists findingsBasic questions
Deep research2–4 minutesComprehensive synthesisAnalysis & insights

How to trigger it

  • Automatically — when you ask a question that fits the "use deep research for" pattern above, Copilot should recognize it and trigger deep research on its own.
  • Manually, if Copilot gives you a code search result instead — ask explicitly, naming the product path, timeframe, and what you want back:
I need you to use the deep research agent to analyze disability claims research.

Research query: "Analyze all research findings in products/disability/ and
products/claim-appeal-status/ from 2022-2025 and identify:
1. Top 5 most frequently mentioned pain points
2. How many studies mentioned each pain point
3. Participant quotes supporting each pain point
4. Which pain points were addressed in subsequent work
5. Links to source research findings files"
  • As a follow-up — if Copilot gives you a quick code-search summary first, you can ask it to "do a deep research analysis on this with quotes and cross-study synthesis" as a next message.

Common use cases

  • Pre-research planning — "I'm planning research on claims status tracking. What existing research should I review, and what do we already know?"
  • Stakeholder briefing — "Summarize all research on the authenticated experience from 2023–2024 for a stakeholder presentation, with key findings, participant quotes, and implementation status."
  • Thematic analysis — "What accessibility issues appear most frequently across health tools research?"
  • Research impact — "How did 2023 profile research influence the current design? Show the path from findings to implementation."

Tips for best results

  • Be specific about timeframe (e.g. "from 2022–2025") and product paths (e.g. "products/disability/").
  • Request explicit outputs — "with participant quotes and implementation status."
  • Ask for synthesis — "identify themes across studies" — rather than a general overview.
  • Expect 2–4 minutes for a real run; don't treat that as stuck.
  • Don't use it for metadata questions like "how many studies?" — a summary file answers that faster.

Troubleshooting

  • Copilot gave a code search result instead of deep research. Not necessarily wrong — if the quick list is good enough, that's fine. For comprehensive synthesis with quotes and implementation tracking, manually trigger deep research as shown above.
  • It's taking a long time. 2–4 minutes is normal — it's reading dozens of research files and synthesizing themes.
  • Can it be used for non-research questions? Yes — it can analyze any content in the repository, including tracing decisions through documentation or patterns across many files.

Sourced from OCTO's internal "Using Deep Research for Comprehensive Research Analysis" Copilot guide — real, currently-documented team guidance, not this prototype's synthesis. Questions go to the #va-copilot Slack channel or @sstrassberg.

Continuous mental health support

  • Don't wait for a Veteran to ask for help — surface support resources (like the Veterans Crisis Line) contextually, at the moments in a flow most likely to be distressing, not only on a generic "contact us" page.
  • Treat this as a design requirement for trauma-adjacent flows (disability claims, mental health intake, bereavement), not an accessibility afterthought.

User control and pacing

  • Let people save progress and leave a form without penalty, and return to exactly where they left off. Recounting traumatic events on demand, on the system's schedule, re-traumatizes.
  • Avoid session timeouts short enough to force a rushed disclosure, and warn generously before any timeout that exists.

Graduated information collection

  • Sequence questions from lower- to higher-sensitivity rather than opening with the hardest disclosure. Group and label sections so a person can see what's coming and prepare.
  • Explain why a sensitive question is being asked and how the answer will be used, right next to the question — not buried in a privacy policy.

Reduced redundancy

  • Never make someone re-enter or re-explain something the system (or another VA process) already has. Re-asking a traumatic detail because two systems don't talk to each other is a design failure, not a data problem.

Expert collaboration

  • Involve clinical, claims, and lived-experience experts (not just end-user researchers) when a flow touches trauma, disability, or loss — they catch harm that a standard usability pass won't.

Contextual guidance

  • Offer help text and examples in place, tailored to where someone likely is emotionally at that step — generic "need help? contact support" links are not enough on high-stress screens.

Source: adapted from the GSA 10x/Digital Corps trauma-informed design work on VA disability claims forms (Form 21-0781) — digitalcorps.gsa.gov: VA trauma-informed approach to digitizing VA disability forms. These six principles were developed for disability claims specifically; treat them as a strong starting checklist for any high-stress VA flow, and validate with your own users and subject-matter experts before assuming they transfer as-is.

Human oversight and accountability stay real

  • Per VA's Trustworthy AI principles, a person — "your doctor, nurse, claims processor, or other VA employee" — remains accountable for outcomes an AI system informs. A chatbot's design should make that human backstop visible and easy to reach, not imply the bot is the final word.
  • AI-assisted features at VA go through two-party review and an ATO (Authorization to Operate) process; a chatbot UX shouldn't quietly outrun what's actually been authorized to make a decision or a recommendation.

Disclose the AI plainly

  • Say up front that the user is talking to an automated system, in plain language, before the conversation starts — not in a footnote.
  • Avoid anthropomorphizing the bot in ways that could lead a Veteran to trust it as a clinical or legal authority it isn't.

Make escalation to a human effortless

  • Offer a clear, always-available path to a human at every turn, not just after repeated failed attempts — especially in claims, health, and benefits contexts.
  • Preserve context across the handoff so the person never has to repeat themselves to the human who picks up.

Be honest about uncertainty and limits

  • Have the bot say when it doesn't know or isn't confident, rather than presenting a guess with the same confidence as a verified answer.
  • Scope the bot to what it's actually authorized and able to do — narrow and reliable beats broad and occasionally wrong, particularly for benefits and health information.

Route crisis situations to real crisis support

  • Detect crisis language and route immediately to the Veterans Crisis Line (988, then press 1) and a human — never let a chatbot attempt to counsel or triage a mental health crisis itself.

Protect data the way VA requires

  • Follow VA's zero-trust, minimal-access approach to data: a chatbot should only access what it needs for the task in front of it, consistent with VA's published Trustworthy AI data protection principles.

The human-oversight, review/ATO, and data-protection points above are sourced from VA's own Trustworthy AI principles — department.va.gov/ai/trustworthy-ai. VA does not publish a single official "chatbot UX patterns" page, so the disclosure, escalation, uncertainty, and crisis-routing guidance above is this prototype's synthesis of that VA policy plus established conversational-AI UX practice — treat it as a starting checklist to validate with your product, policy, and clinical stakeholders, not an official VA design spec.

Section 4

Understanding MCP

The Model Context Protocol (MCP) is an open standard that lets AI tools connect to external services — your design files, databases, APIs, and more. Think of it as giving your AI assistant eyes and hands beyond just code.

1
What Is MCP?
The bridge between AI and your tools
▼

MCP (Model Context Protocol) is a standard created by Anthropic that defines how AI assistants communicate with external tools and data sources. Without MCP, an AI can only see the text you type. With MCP, it can:

  • Read your Figma designs and understand component structure
  • Access your file system to read and write code
  • Query APIs and databases for real data
  • Run commands in your terminal
  • Search the web for documentation and references
Term Meaning
MCP Server A small program that connects a specific tool (Figma, GitHub, Slack, etc.) to AI
MCP Client The AI application (VS Code Copilot, Claude Code, Cursor, etc.) that talks to MCP servers
Tools Actions the MCP server exposes — like "get design," "create file," "search"
Resources Data the MCP server can provide — like file contents, design metadata, etc.
2
How MCP Works in VS Code
Configure MCP servers for Copilot
▼

VS Code supports MCP servers through its settings. When you configure an MCP server, GitHub Copilot (in Agent mode) can use its tools.

Where to configure:

  • User-level: In your VS Code settings (settings.json) — available in all projects
  • Project-level: In a .vscode/mcp.json file — shared with your team via the repo

The configuration format looks like this:

// .vscode/mcp.json { "servers": { "my-server-name": { "type": "stdio", "command": "npx", "args": ["-y", "@example/mcp-server"], "env": { "API_KEY": "${input:apiKey}" } } }, "inputs": [ { "id": "apiKey", "description": "API key for the service", "type": "promptString", "password": true } ] }
The ${input:apiKey} syntax prompts you for the value when the server starts, so you never have to hard-code secrets in your config files.

Section 5

Setting Up Figma MCP

The Figma MCP server lets AI tools read your designs, extract styles, understand component structure, and even write designs back into Figma. It's the bridge between your design files and code.

1
Get a Figma Access Token
Create a personal access token in Figma
▼
  1. Open Figma and click your profile icon in the top-left
  2. Go to Settings
  3. Scroll down to Personal access tokens
  4. Click Generate new token
  5. Give it a descriptive name like "MCP Server Access"
  6. Set the expiration (90 days is a good balance of security and convenience)
  7. For scopes, enable at minimum:
    • File content — Read access (required)
    • File content — Write access (needed for code-to-design)
    • Dev resources — Read and Write (for Code Connect)
  8. Click Generate token and copy it immediately — you won't be able to see it again
Keep your token secret. Never commit it to a repo, paste it in Slack, or share it in a document. Store it in a password manager or use environment variables.
2
Configure Figma MCP in VS Code
Add the Figma MCP server to your project
▼

Create a .vscode/mcp.json file in your project root:

// .vscode/mcp.json { "servers": { "figma": { "type": "stdio", "command": "npx", "args": ["-y", "figma-developer-mcp", "--stdio"], "env": { "FIGMA_API_KEY": "${input:figmaApiKey}" } } }, "inputs": [ { "id": "figmaApiKey", "description": "Your Figma Personal Access Token", "type": "promptString", "password": true } ] }

When you start a Copilot Agent session, VS Code will prompt you for the Figma token. It's stored securely in your session and never written to disk.

Alternative: Environment variable. If you prefer not to be prompted each time, set FIGMA_API_KEY in your shell profile (~/.zshrc or ~/.bashrc) and replace the env value with just "FIGMA_API_KEY": "${env:FIGMA_API_KEY}".

Using Figma MCP with Copilot
Step-by-step design-to-code workflow

Here's how to go from a Figma design to code using Copilot + Figma MCP:

  1. Open your project in VS Code

Design prototypes (Figma)

  • Start from the VADS Component Library in Figma — it's built for static mockups and interactive prototypes, using the same components, tokens, and variants that ship in code, so a clickable prototype stays true to what will actually be built.
  • The VADS Example Library and Templates, Patterns, and Forms library give you copy-paste starting points for common flows (multi-step forms, hub pages, confirmation pages) instead of building a prototype screen from scratch.
  • See design.va.gov's "Figma at VA" guidance (under About → Designers) for how these libraries are kept in sync and connected to a new file.

Coded prototypes

  • For a higher-fidelity, in-browser prototype, pull the real web components from the CDN or npm package (@department-of-veterans-affairs/component-library) — the same approach this AI Workbench prototype itself uses — rather than hand-coding lookalike markup.
  • Storybook (design.va.gov/storybook) is the fastest way to explore a component's actual states, props, and variants before wiring it into a prototype — see the VA Design System tab for details.

VA doesn't publish a single official product named "VA Prototype Kit" the way some government design systems do (e.g. GOV.UK's Prototype Kit). This tab is a practical guide to the real prototyping resources that do exist across the VADS ecosystem — the Figma libraries at design.va.gov/about/designers/design-libraries and the component-library package at github.com/department-of-veterans-affairs/component-library — swap in your team's actual internal prototyping tool or shortcut here if one exists that isn't captured above.

What VADS is

  • The VA Design System provides design guidelines, web components, and patterns for building accessible, consistent, Veteran-centered services on VA.gov — built on a fork of the U.S. Web Design System (USWDS v1.6.10) and aligned to the 21st Century IDEA Act.
  • Critical rule: any UI element that can use a VADS web component must use it. A custom-coded lookalike is an "imposter component" — a launch-blocking issue at Staging Review, with the only exception being plain <button>/<a> elements using VADS classes for default variations.

Components → templates → patterns

  • Component — the smallest reusable unit, e.g. va-button, va-accordion, va-alert.
  • Template — a page layout composing multiple components, e.g. a form step or a confirmation page.
  • Pattern — a multi-page or multi-step solution, e.g. navigating a benefit application or signing in.

Storybook

  • design.va.gov/storybook is the live, interactive component catalog — every VADS web component with its real props, variants, and states, runnable in the browser.
  • Use it to check a component's actual API and behavior before wiring it into a page, rather than guessing from a screenshot or an older doc — props and variants do change between releases (the component library ships on a roughly two-week sprint cadence).
  • Pairs naturally with the Figma VADS Component Library: design in Figma, confirm the real interactive behavior in Storybook, then implement with the same component tag.

Foundations

  • Typography — Source Sans Pro for headings and body, Roboto Mono for code.
  • Spacing — an 8pt system (4/8/12/16/20/24/32/40/48px tokens); use the spacing tokens, not raw pixel values.
  • Color — always reference the token (--vads-color-primary, --vads-color-success, etc.), never a hardcoded hex, so palette updates propagate automatically.
  • Layout — a 12-column flexbox grid, 1000px max content width, mobile-first from a 320px baseline.

Source: design.va.gov and design.va.gov/storybook — the VA Design System's own published documentation and component catalog (referenced component-library release: v56.x).

The stack

  • React 16+ (functional components and hooks), bundled with a custom Webpack config, styled with CSS Modules plus VADS design tokens as CSS custom properties.
  • Multi-step benefit forms are built with the VA Forms Library (platform/forms-system, based on react-jsonschema-form) rather than hand-rolled form state.
  • State management is Redux; API calls go through the platform's apiRequest utility (handles CSRF tokens, auth headers, and error normalization) rather than raw fetch.
  • Testing: Jest + React Testing Library for units, Cypress for end-to-end, axe-core for automated accessibility checks — all required before a feature can pass Staging Review.

Where the code lives

  • Production code ships to the vets-website monorepo, under src/applications/<your-app>/, with shared platform utilities under src/platform/.
  • Each application folder typically has its own manifest.json, components/, containers/, reducers/, actions/, and a config/form.js when it's a Forms Library app.

Local development

  • Clone vets-website, install with Yarn (Node 18+), then yarn watch to run the dev server — or yarn build --entry src/applications/<app>/app-entry.jsx to build just one app for a faster loop.
  • A mock API server is available for working against fixture data without a live vets-api backend.

Governance: the Collaboration Cycle

  • Every feature passes four checkpoints before it ships: Design Intent (alignment with VADS and the Veteran experience), Midpoint Review (functional build reviewed by Platform), Staging Review (accessibility/508, QA, content, IA), and a Privacy/Security Review (PII handling, data flows).
  • Automatic Staging Review blockers: imposter components, critical axe accessibility violations, a missing va-need-help on a form step, a missing va-omb-info on a form's intro page, and hardcoded phone numbers instead of <va-telephone>.

Source: the VA Platform's own documentation — depo-platform-documentation.scrollhelp.site, github.com/department-of-veterans-affairs/vets-website, and the Collaboration Cycle guidance referenced throughout this project.
